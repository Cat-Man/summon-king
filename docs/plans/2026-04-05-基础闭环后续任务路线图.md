# 基础闭环后续任务路线图 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在当前首页-地图-副本-修行-成长的首条闭环基础上，继续把 H5 版本推进到更完整的可玩 Alpha，优先补齐首页导流、奖励回写和玩法之间的自然跳转，同时提前补齐会影响后续扩展的规则层与模块边界。

**Architecture:** 后续任务按“先补当前可玩主循环，再抽离统一规则/资产/战斗底座，最后再扩联盟/商业化/后台/渠道壳”的顺序推进。优先避免继续在各玩法里散落奖励、解锁、战力和结算逻辑，减少后面补 `asset`、`pet`、`battle`、持久化时的返工。

**Tech Stack:** Vue 3 + TypeScript + Pinia + Vite；Go + Gin；当前以内存仓储为主，后续逐步接入 MySQL / Redis。

### Task 1: 首页做成下一步动作中枢，并接入塔玩法真实奖励同步

**Why first:**
- 当前首页还不是完整的业务分发中枢，growth / tower / arena / ranking 更多依赖全局导航直达，而不是被主循环自然带出。
- 当前塔页面和后端已存在，但还只是“层数 + 文案奖励”，没有真实资源结算。
- 这会直接限制塔玩法成为真实日常入口，也会让首页看不到“今天下一步该做什么”。

**Current evidence:**
- `apps/backend/internal/modules/tower/service.go`
- `apps/backend/internal/modules/tower/repository.go`
- `apps/backend/internal/modules/home/service.go`
- `apps/game-web/src/pages/home/HomePage.vue`
- `apps/game-web/src/pages/tower/PagodaPage.vue`
- `apps/game-web/src/pages/tower/SpiritTowerPage.vue`

**Target:**
- 首页聚合 `growth / tower / arena / ranking` 的入口卡片
- 首页根据当前状态给出单一“下一步推荐动作”
- 通天塔 / 战灵塔挑战后写回 `growth.Wallet`
- 首页 `overview` 自动同步塔玩法收益后的资源变化
- 前端塔页展示最近真实奖励而不是纯文案

### Task 2: 竞技场奖励与排行榜刷新闭环

**Why second:**
- 当前竞技场只有连胜计数，没有奖励，没有驱动资源成长。
- 排行榜虽然已能聚合，但没有和竞技场挑战结果形成明确闭环。

**Current evidence:**
- `apps/backend/internal/modules/arena/service.go`
- `apps/backend/internal/modules/arena/repository.go`
- `apps/backend/internal/modules/ranking/service.go`
- `apps/game-web/src/pages/arena/ArenaPage.vue`
- `apps/game-web/src/pages/ranking/RankingPage.vue`

**Target:**
- 竞技场胜负发放基础奖励或积分
- 排行榜能更明确反映竞技场结果
- 首页或竞技场页能看到挑战结果对成长的影响
- 至少形成 `首页/日常入口 -> 竞技场 -> 排行榜/首页` 的回流路径

### Task 3: 地图解锁条件升级为组合条件，并给出养成去向提示

**Why third:**
- 当前地图副本入口已支持 `unlock_spirit_power`，但条件仍然过于单一。
- 下一步最自然的是把地图变成“成长去哪里”的导航页，而不是仅仅禁用按钮。

**Current evidence:**
- `apps/backend/internal/modules/dungeon/domain.go`
- `apps/backend/internal/modules/dungeon/service.go`
- `apps/game-web/src/pages/maps/WorldMapPage.vue`
- `apps/game-web/src/pages/growth/*.vue`

**Target:**
- 入口条件支持 `spirit_power + bone_level + soul_pieces` 的组合
- 未解锁时显示“去战骨/魔魂提升”的明确提示
- 前端从地图直接引导到对应成长页

### Task 4: 抽离统一奖励/资产结算层，停止各玩法直接写钱包

**Why fourth:**
- 当前 `dungeon` 已直接操作 `growth.Wallet`，后续塔、竞技场如果继续沿用，会让奖励规则分散在各玩法模块。
- 总设计里已冻结“所有资产变更只走 asset 模块”，现在还没实现。

**Current evidence:**
- `apps/backend/internal/modules/dungeon/service.go`
- `apps/backend/internal/modules/growth/repository.go`
- 设计文档：`docs/plans/2026-03-21-召唤之王详细设计文档.md`

**Target:**
- 至少先抽一个统一 reward applier / asset service
- 副本、塔、竞技场都改走统一入口
- 为后续商城、签到、联盟奖励留出共用通道

### Task 5: 补 `pet` / `battle` 最小骨架，替换当前玩法里的“伪战斗”

**Why fifth:**
- 当前副本、塔、竞技场基本都是状态推进和文案结果，还没有统一战斗或阵容概念。
- 如果继续先做更多玩法，再回头补 `battle`，返工会很大。

**Current evidence:**
- 路由和页面已覆盖多玩法，但后端模块中没有 `pet`、`battle`
- 设计文档 4.6 已明确要求存在 `pet`、`battle`

**Target:**
- 建最小阵容快照
- 建统一战斗结果结构
- 先让副本 / 塔 / 竞技场共享一套结果模型，即便仍是简化数值判定

### Task 6: 现有模块从内存仓储迁移到真实持久化

**Why sixth:**
- 当前 `dungeon`、`tower`、`arena`、`growth` 都以内存仓储为主，开发方便，但会限制联调和跨会话验证。
- 在玩法数量继续增加前迁移，成本比后面统一迁移低。

**Current evidence:**
- `apps/backend/internal/modules/*/repository.go`
- 设计文档已冻结 `MySQL + Redis`

**Target:**
- 先迁移 `account / growth / dungeon / arena / tower`
- Redis 至少承担会话与排行榜缓存
- 为后续 worker / 定时任务做状态基础

### Task 7: 联盟、商业化、后台、渠道壳作为第二阶段扩展

**Why last:**
- 这些都在总设计里，但当前代码库几乎还没开始。
- 在核心可玩主循环和统一结算/战斗底座未稳定前，不适合优先展开。

**Current evidence:**
- `apps/admin-web` 只有 `package.json`
- `apps/mini-shell` 只有 `project.config.json`
- 后端暂无 `alliance`、`commerce`、`gm`、`config` 模块

**Target:**
- `alliance`：联盟、火能修行、盟战
- `commerce`：VIP、礼包、签到、兑换
- `admin-web`：配置后台 / GM 后台最小壳
- `mini-shell`：登录 / 支付 / 分享桥接

### 默认执行顺序

1. `首页做成下一步动作中枢，并接入塔玩法真实奖励同步`
2. `竞技场奖励与排行榜刷新闭环`
3. `地图解锁条件升级为组合条件，并给出养成去向提示`
4. `抽离统一奖励/资产结算层`
5. `补 pet / battle 最小骨架`
6. `现有模块迁移到真实持久化`
7. `联盟 / 商业化 / 后台 / mini-shell`

### 执行约束

- 默认后续按上面的顺序连续推进，不再每完成一阶段都向用户确认。
- 只有遇到以下情况才中断询问：
  - 现有未提交改动与新任务直接冲突
  - 需要破坏性迁移或重写既有接口
  - 需要用户提供外部资源、账号、密钥或业务口径
